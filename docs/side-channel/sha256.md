# Side-Channel Notes — P-3: SHA-256

**Module:** `ctcrypto::Sha256` / `ctcrypto::sha256` —
[`include/ctcrypto/sha256.hpp`](../../include/ctcrypto/sha256.hpp),
[`src/sha256.cpp`](../../src/sha256.cpp)
**Satisfies:** FR-4, FR-5, NFR-1…NFR-3, SCN-1/SCN-2
**Status:** Educational — **NOT for production**. Read
[`overview.md`](overview.md) first; it holds the shared threat model and limitations.

---

## 1. Constant-time technique(s) used

SHA-256 is **naturally branchless**: the compression function is pure 32-bit integer
arithmetic (additions, XOR, AND, NOT, fixed rotations/shifts) with no data-dependent control
flow, so no special masking is needed.

- **No secret-dependent branches.** The round functions (`Ch`, `Maj`, `Σ0/Σ1`, `σ0/σ1`) are
  computed with `&`, `^`, `~`, and fixed-distance `rotr`/shift — the same operations every
  round, for every input.
- **No secret-dependent indexing.** The round-constant table `K[64]` and the message
  schedule `w[64]` are indexed **only by the public round counter `t`**, never by message
  content. Message bytes are loaded into big-endian words with explicit shift/mask
  (`load_be32`), not by a secret-indexed lookup.
- **Public-length control flow only.** `update` fills a partial block, consumes whole blocks,
  and stashes the remainder using loop bounds derived solely from the **public** input
  length. Padding in `finalize` is driven by the public message length, not by content.
- **No pointer punning.** Word load/store uses explicit byte arithmetic (`load_be32` /
  `store_be32`) rather than `reinterpret_cast`/`memcpy` type punning.
- **Best-effort state hygiene.** The per-block message schedule `w` is wiped after each
  `compress`; `state_` and `buffer_` are wiped on `finalize` and in the destructor via
  `secure_wipe` (see the `wipe` limitations in the overview).

## 2. What is treated as secret

- The **message bytes**, to the extent the caller feeds secret data. The engine is written to
  touch no secret-dependent branch or index *regardless* of whether the input is secret.
- Internal hash state (`state_`, `buffer_`, the schedule `w`) is treated as secret-derived
  and wiped best-effort.

What is **public**:

- The message length (and therefore all loop bounds and the padding layout) and the output
  digest. SHA-256's control flow is not secret-dependent by construction.

## 3. Known limitations / threats NOT mitigated

In addition to everything in [`overview.md §2.3 and §3`](overview.md):

- **Length is not hidden.** The number of blocks processed — and therefore timing — scales
  with the public message length. This primitive does not conceal input length.
- **`std::memcpy` / `std::memset` usage.** These are used only to move bytes at
  public-length, public-position boundaries (buffer fill, padding, reset). They are not used
  for any secret-dependent decision, but their own timing is not assumed constant-time.
- **`secure_wipe` is best-effort.** Register/stack copies, spills, and swapped pages may
  retain hash-state material; see the overview.
- **No cache / micro-architectural / power / EM / fault protection** — see the overview.
- **Compiler variance.** As with all primitives here, constant-time behavior is not
  guaranteed across compilers, optimization levels, and hardware (SCN-2).

## 4. How it was reasoned about / checked

- **Code review** confirmed: table/schedule indexing by the public round counter only, no
  secret-dependent branch, loop bounds from public lengths, explicit byte I/O, and
  known-answer correctness against FIPS 180-4 vectors in the test suite.
- **QA verification:** 58/58 GoogleTest pass including SHA-256 known-answer and edge cases;
  ASan+UBSan clean on GCC 13.3 and Clang 18.1. SHA-256 was not a focus of the `-O2` assembly
  spot-check (that targeted the explicit constant-time helpers and HMAC verify), since its
  constant-time property is structural rather than mask-based.

**Limits of this evidence:** correctness and sanitizer coverage are strong, but the
constant-time claim rests on the structural branch/index-freedom confirmed by review, not on
a formal proof or exhaustive assembly inspection. See [`overview.md §4.1`](overview.md).
